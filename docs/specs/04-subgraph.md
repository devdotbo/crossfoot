# 04. Feed subgraph (Midas customFeed family and svZCHF)

Build plan item 3. Large. Lives in `subgraph/` of this repository.

## Goal

One subgraph on Ethereum mainnet that indexes the posted side of two feed
families with one schema: the 60 bounded Midas custom aggregator feeds
(POSTED: an admin posts a value through a guarded or unguarded setter) and
svZCHF (DERIVED: the value follows from Frankencoin protocol state). Every
round records which setter posted it, how far it moved from the previous
answer, and which bound was in force, so that one query returns the latest
posted state per feed across families and a consumer can find every unchecked
post over the bound without an archive node. Crossfoot's verdicts and bundle
hashes stay off chain (review C5); the subgraph carries on-chain facts only.

## Non-goals

- No Crossfoot output in the schema: no verdict, no bundle root, no
  consumer action (`00-architecture.md` Q2, default kept).
- No claim on failed setter attempts: failed transactions emit no events;
  `02-midas-family-replay.md` R13 keeps them from Blockscout.
- No timeseries or aggregation entities, no other chain. Call handlers exist
  only for the four setter functions (R6a); no other call is indexed.
- No recomputation of svZCHF in mappings: derived rounds record `price()`
  at each state transition; MODEL_MATCH is Crossfoot's job.

## Decisions on the six feasibility points

| # | Question | Default | Reason |
|---|---|---|---|
| D1 | 60 or 66 data sources | 60 | The six Dv/Rv wrappers emit no events and revert on the bound getters; as data sources they index nothing. They stay in `config/midas-mainnet.json` as `derived` (02 R2) and the consumer lists them as wrappers of a base feed. |
| D2 | Fourth `Path` value | `PROTOCOL` | A filter on `path: UNCHECKED` must never need a second filter on family to be correct. |
| D3 | Derived round answer | `price()` per state transition | About 145 calls in total; per RateChanged only (4 rounds) is too coarse for a staleness reading. |
| D4 | Studio or publish | Studio for the demo; publish to Arbitrum One as a stretch | The Studio endpoint is a Graph provider on the published track wording; publishing costs Arbitrum gas (amount unverified) plus a curation tax only if signalling, and cannot be undone if the schema still moves. Publish once the schema is final (commit plan 1e). |
| D5 | Three-argument selectors as SAFE and UNCHECKED | Yes, by name, raw `selector` kept | The growth feed's implementation source is unread; the consumer marks rounds with `0x92260352` or `0x2b6e02c7` as "selector semantics unverified" (05 R6) instead of the subgraph guessing. |
| D6 | AdminChanged handler and Poster entity | Poster yes, AdminChanged no | Poster makes "one key per feed" one query. The 60 AdminChanged events are one per proxy at deployment (own inference from the count), so they carry no change history; the admin can be read once when needed. |

## Behaviour

Manifest and sources:

- R1. `subgraph/subgraph.yaml` is generated by `subgraph/scripts/gen-manifest.ts`
  from `subgraph/feeds.json` (format below) and a template: one data source
  per bounded feed with `source.address`, `source.startBlock` = creation
  block, `context` {issuer, product, registryKey}, and the ABI named in the
  row; plus the Frankencoin module source. The generated file is committed
  and regeneration is byte identical.
- R2. `subgraph/feeds.json` holds exactly the 60 `bounded` entries of
  `config/midas-mainnet.json` (same addresses, checksummed) and none of the
  six `derived` ones. Start blocks: earliest 20,578,232 (mTBILL), mRE7
  21,786,070, growth feed 24,798,563, latest 25,831,643 (mArbBTC).
- R3. Two feed ABIs: `CustomFeed.json` (three-argument AnswerUpdated,
  generated from the verified mRE7 implementation source, not from a
  Chainlink ABI) for 59 feeds, and `CustomFeedGrowth.json` (four-argument)
  for the growth feed. Both ABIs carry `Initialized`, `Upgraded` and the
  five getters. A manifest without the second ABI is a defect (family count
  59 instead of 60). No data source omits `address`.
- R4. Versions pinned: specVersion 1.3.0, apiVersion 0.0.9, graph-ts 0.38.2,
  graph-cli 0.97.1 (`bunx`, never `npx`). Every contract call in a mapping
  uses a `try_` variant; a revert never reaches the handler.

Midas mappings (`subgraph/src/midas.ts`, `subgraph/src/shared.ts`):

- R5. `handleInitialized` on version 1 creates the Feed: `family: POSTED`,
  `issuer`, `product`, `registryKey` from the data source context,
  `description()` and `decimals()` via `try_`, `createdBy` =
  `transaction.from`, counters zero. On every Initialized event it reads
  `maxAnswerDeviation()`, `minAnswer()`, `maxAnswer()` via `try_` at the
  event block and writes a BoundChange (old values from the Feed, new
  values, `initializerVersion`, `caller` = `transaction.from`, `detectedBy:
  INITIALIZED`); `changed` is true only when a previous value existed and
  differs, so version 1 is `changed: false`. It then updates the Feed's
  bound fields and `boundChangeCount`.
- R6. `handleAnswerUpdated` (both ABIs) writes one immutable Round per
  event: `roundId`, `answer`, `updatedAt` from the topics; `extra` from the
  unindexed int80 on the growth feed, else null; `block`, `blockTimestamp`,
  `tx`, `logIndex`, `poster` = `transaction.from`. Path rule, applied to the
  outer transaction only: if `transaction.to` equals `event.address` and
  `transaction.input.length >= 4`, `selector` = the first four bytes and
  `path` is `SAFE` for `0x89d6e95f` or `0x92260352`, `UNCHECKED` for
  `0xa4381d1f` or `0x2b6e02c7`, else `UNKNOWN`, and `attributedBy` is
  `TRANSACTION`; if the transaction did not target the feed (Safe,
  multicall, relayer), `selector` is null, `path` is `UNKNOWN` and
  `attributedBy` is `NONE`. Inner calldata is never parsed. The handler also
  writes or extends a `PostTx` record (id = feed ++ tx hash: first roundId,
  count of rounds of this feed in the transaction, rounds attributed so far).
- R6a (correction of 2026-09-02, raw/codex-review-verdict-2026-09-02.md).
  Every Midas data source declares `callHandlers` on `setRoundDataSafe(int256)`,
  `setRoundData(int256)` (59 feeds) or the three-argument variants (growth
  feed). Call triggers fire at any call depth, and graph-node orders the
  call triggers of a transaction after its event triggers, so each setter
  call handler loads the `PostTx` of (call.to, tx hash), takes the next
  unattributed round, and sets `path` from the handler's selector,
  `selector`, `caller` = `call.from` (the Safe for routed posts, the poster
  for direct ones) and `attributedBy: CALL`, adjusting `uncheckedCount` on
  the Feed and the Poster when the path moves to or from UNCHECKED. The
  Round stays immutable: graph-node accepts the write inside the creation
  block. A direct EOA post is re-attributed with identical values, so at
  head every Round reads `attributedBy: CALL`; the 215 Safe-routed rounds of
  mTBILL, mBASIS, mBTC, mEDGE, mMEV and mRE7 (28 of them over-bound
  unchecked posts) are attributed this way. The event handler stays the
  source of truth for rounds; a call without a round in its transaction
  changes nothing. `feeds.json` carries a `callHandlers` switch; with it off
  the manifest has event handlers only and the rounds above stay UNKNOWN
  (fallback documented in `DEPLOYMENT.md`).
- R7. `first` is true when the Feed has no `latestRound`. `previousAnswer`
  is the Feed's `latestAnswer`; `secondsSincePrevious` = `updatedAt` minus
  the Feed's `latestUpdatedAt`; `deviationFromPrevious` =
  `|answer - previousAnswer| * 100000000 * 100 / previousAnswer` in BigInt
  arithmetic on the absolute difference (the contract's integer formula,
  `model::mtbill::deviation`), null when `previousAnswer` is absent or zero.
  Check value: mRE7 round 36, |106438116 - 108859885| against 108859885
  gives 222466613. Rounds within one block are applied in log index order,
  so a second post in the same block uses the first as its previous.
- R8. `boundAtPost` comes from a declared eth_call on the AnswerUpdated
  handler (`Feed[event.address].maxAnswerDeviation()`, manifest `calls`),
  read through `try_`; null if the call fails. When it differs from
  `Feed.bound`, the handler writes a BoundChange with `detectedBy: ROUND`
  (old = Feed.bound, new = the call result, `initializerVersion: 0`,
  `changed: true`) before writing the Round, and updates `Feed.bound`.
  `overBound` = `!first && deviationFromPrevious != null && boundAtPost != null
  && deviationFromPrevious > boundAtPost`.
- R9. After each Round the handler updates the Feed (`latestRound`,
  `latestAnswer`, `latestUpdatedAt`, `roundCount`, `uncheckedCount` for
  `path: UNCHECKED && !first`, `overBoundCount`) and the Poster (`id` =
  `poster`, `feeds` extended if new, `roundCount`, `uncheckedCount`,
  `firstSeenBlock`, `lastSeenBlock`). Posters exist for POSTED feeds only.
- R10. `handleUpgraded` writes an immutable Upgrade with id = feed address
  ++ tx hash (one Upgraded per proxy per transaction; a second one in the
  same transaction gets the id extended by its log index and is not joined),
  `implementation`, `logIndex`, `withInitializer: false`, and sets
  `Feed.implementation` and `upgradeCount`. The Upgraded event precedes the
  Initialized event of the same transaction (ERC1967 `upgradeToAndCall`
  emits before it delegatecalls the initializer), so `handleInitialized`
  loads the Upgrade by (feed, tx hash) and sets `withInitializer: true`;
  the write is inside the creation block, which graph-node allows on
  immutable entities. Deterministic, no mutable Upgrade needed. Deployment
  transactions carry Initialized(1) after Upgraded, so `withInitializer` is
  true for the 60 deployment upgrades as well as the four upgradeAndCall
  ones (expected 64 of 98).

Frankencoin mappings (`subgraph/src/frankencoin.ts`):

- R11. The svZCHF Feed has `id` = the vault address (the asset a consumer
  holds and the address `site/data/feeds.json` carries for the svZCHF
  row), `family: DERIVED`, `issuer: "Frankencoin"`, `product: "svZCHF"`,
  `decimals: 18`, `inputsFrom` = the module address, `bound` null. It is
  created by the first module event; `createdAtBlock` is that event's block
  (22,536,327, the module's deployment) and is documented as such.
- R12. `handleRateChanged` writes RateChange (`ratePPM`, `applier` =
  `transaction.from`, `proposal` = the latest RateProposal with the same
  `nextRatePPM` and `nextChange <= blockTimestamp`, else null);
  `handleRateProposed` writes RateProposal. Both are written from the
  module's start block regardless of the vault.
- R13. `handleSaved`, `handleWithdrawn`, `handleInterestCollected` (topic1 =
  vault by manifest filter) write a VaultFlow (`kind`, `account`, `amount`
  from the first data word, `referralFee` from the second on
  InterestCollected). From the vault deployment block 24,118,272 on, these
  handlers and `handleRateChanged` also write a derived Round: `path:
  PROTOCOL`, `roundId` = `Feed.roundCount + 1`, `answer` = vault `price()`,
  `totalAssets`, `totalSupply` via `try_` at the event block, `updatedAt` =
  block timestamp, `poster` = `transaction.from`, `trigger` naming the
  event, `first`, `previousAnswer`, `secondsSincePrevious`,
  `deviationFromPrevious` as in R7, `boundAtPost` null, `overBound` false.
  `VaultFlow.round` links the Round. Below block 24,118,272 no Round is
  written (the vault has no code).

## Data and file formats

`subgraph/feeds.json` (generator input, one row per bounded feed):

```json
{"family": "midas-customfeed", "chain_id": 1, "feeds": [
  {"product": "mRE7", "key": "customFeed", "issuer": "Midas",
   "address": "0x0a2a51f2f206447dE3E3a80FCf92240244722395",
   "startBlock": 21786070, "abi": "CustomFeed"},
  {"product": "mGLOBAL", "key": "customFeedGrowth", "issuer": "Midas",
   "address": "0x66Aa9fcD63DF74e1f67A9452E6E59Fbc67f75E38",
   "startBlock": 24798563, "abi": "CustomFeedGrowth"}]}
```

Generated manifest, per Midas source: `name: Midas_mRE7_customFeed`,
`network: mainnet`, `source {address, abi, startBlock}`, `context {issuer,
product, registryKey}`, handlers AnswerUpdated (with `calls: {bound:
CustomFeed[event.address].maxAnswerDeviation()}`), Initialized, Upgraded,
call handlers on the two setters of the ABI (R6a), `file: ./src/midas.ts`.
`indexerHints: prune: never`, because the consumer replays with
`block: {number: $block}`. The module source carries the five handlers of R12
and R13 with `topic1: [<vault>]` on the three flow events.

Final schema (`subgraph/schema.graphql`; the feasibility draft plus
`Feed.inputsFrom`, `Feed.latestRateProposal` (the join input of R12),
`Round.caller`, `Round.attributedBy`, `Upgrade.logIndex` and the `PostTx`
join record of R6; ids are `tx ++ logIndex` unless stated in R6, R6a and
R10; `Round.id` is feed address ++ roundId as 32 bytes;
`BoundChange.initializerVersion` is 0 when `detectedBy` is `ROUND`;
`extra`, `totalAssets`, `totalSupply`, `trigger` are family-specific and
null elsewhere):

```graphql
enum Family { POSTED DERIVED }
enum Path { SAFE UNCHECKED UNKNOWN PROTOCOL }
enum FlowKind { SAVED WITHDRAWN INTEREST_COLLECTED }

type Feed @entity {
  id: Bytes!  family: Family!  issuer: String!  product: String!  registryKey: String
  description: String  decimals: Int!  inputsFrom: Bytes
  bound: BigInt  minAnswer: BigInt  maxAnswer: BigInt  implementation: Bytes
  createdAtBlock: BigInt!  createdAtTimestamp: BigInt!  createdBy: Bytes!
  latestRound: Round  latestAnswer: BigInt  latestUpdatedAt: BigInt  latestRateProposal: RateProposal
  roundCount: Int!  uncheckedCount: Int!  overBoundCount: Int!  boundChangeCount: Int!  upgradeCount: Int!
  rounds: [Round!]! @derivedFrom(field: "feed")
  boundChanges: [BoundChange!]! @derivedFrom(field: "feed")
  upgrades: [Upgrade!]! @derivedFrom(field: "feed")
  posters: [Poster!]! @derivedFrom(field: "feeds")
}
type Round @entity(immutable: true) {
  id: Bytes!  feed: Feed!  roundId: BigInt!  answer: BigInt!  updatedAt: BigInt!
  block: BigInt!  blockTimestamp: BigInt!  tx: Bytes!  logIndex: BigInt!  poster: Bytes!  caller: Bytes
  path: Path!  selector: Bytes  attributedBy: String!  first: Boolean!
  previousAnswer: BigInt  secondsSincePrevious: BigInt  deviationFromPrevious: BigInt
  boundAtPost: BigInt  overBound: Boolean!  extra: BigInt
  totalAssets: BigInt  totalSupply: BigInt  trigger: String
}
type PostTx @entity(immutable: true) {
  id: Bytes!  feed: Feed!  tx: Bytes!  firstRoundId: BigInt!  count: Int!  attributed: Int!
}
type BoundChange @entity(immutable: true) {
  id: Bytes!  feed: Feed!  initializerVersion: Int!  changed: Boolean!  detectedBy: String!
  oldBound: BigInt  newBound: BigInt  oldMinAnswer: BigInt  newMinAnswer: BigInt
  oldMaxAnswer: BigInt  newMaxAnswer: BigInt
  block: BigInt!  blockTimestamp: BigInt!  tx: Bytes!  caller: Bytes!
}
type Upgrade @entity(immutable: true) {
  id: Bytes!  feed: Feed!  implementation: Bytes!  withInitializer: Boolean!
  block: BigInt!  blockTimestamp: BigInt!  tx: Bytes!  logIndex: BigInt!
}
type Poster @entity {
  id: Bytes!  feeds: [Feed!]!  roundCount: Int!  uncheckedCount: Int!
  firstSeenBlock: BigInt!  lastSeenBlock: BigInt!
}
type RateChange @entity(immutable: true) {
  id: Bytes!  feed: Feed!  ratePPM: Int!  applier: Bytes!  proposal: RateProposal
  block: BigInt!  blockTimestamp: BigInt!  tx: Bytes!
}
type RateProposal @entity(immutable: true) {
  id: Bytes!  feed: Feed!  proposer: Bytes!  nextRatePPM: Int!  nextChange: BigInt!
  block: BigInt!  blockTimestamp: BigInt!  tx: Bytes!
}
type VaultFlow @entity(immutable: true) {
  id: Bytes!  feed: Feed!  kind: FlowKind!  account: Bytes!  amount: BigInt!  referralFee: BigInt
  block: BigInt!  blockTimestamp: BigInt!  tx: Bytes!  logIndex: BigInt!  round: Round
}
```

The three queries (`subgraph/queries/`; the agent supplies variables and,
on replay, `block: {number: $block}`):

```graphql
query FeedStatus { _meta { deployment block { number hash timestamp } hasIndexingErrors }
  feeds(first: 100, orderBy: latestUpdatedAt) { id family issuer product decimals bound
    minAnswer maxAnswer latestAnswer latestUpdatedAt roundCount uncheckedCount
    overBoundCount latestRound { roundId path overBound } } }
query WindowFindings($since: BigInt!, $resultBlock: BigInt!) {
  overBound: rounds(where: {path: UNCHECKED, first: false, blockTimestamp_gte: $since}, first: 100) {
    feed { id product } roundId answer previousAnswer deviationFromPrevious boundAtPost
    overBound selector poster tx block blockTimestamp }
  unknown: rounds(where: {path: UNKNOWN, blockTimestamp_gte: $since}, first: 1000) { feed { id } roundId tx block }
  boundChanges(where: {changed: true, blockTimestamp_gte: $since}) { feed { id } oldBound newBound
    oldMinAnswer newMinAnswer oldMaxAnswer newMaxAnswer block tx caller }
  rateChanges(where: {block_gt: $resultBlock}) { feed { id } ratePPM block tx } }
query FeedTimeline($feed: Bytes!) { feed(id: $feed) { product description bound roundCount
    uncheckedCount overBoundCount boundChanges(orderBy: block) { block initializerVersion oldBound newBound changed caller tx }
    rounds(orderBy: roundId, first: 1000) { roundId answer updatedAt path selector first
      deviationFromPrevious boundAtPost overBound secondsSincePrevious tx block } } }
```

## Corrections 2026-09-02

Applied after the external review of the whole project on 2026-09-02
(research repository `raw/codex-review-verdict-2026-09-02.md`, blockers
3.1 and 3.2, plus the consumer's block variable, blocker 3.3). Where a
paragraph above reads differently, this section wins.

- C1. Safe-routed rounds get a path. R6 labels every round whose outer
  transaction does not target the feed `UNKNOWN`. That covers the 215
  Safe-era rounds of the six oldest feeds and hides their 28 unchecked
  posts over the bound, so the subgraph alone reproduces the 29-on-14 base
  from transaction lists and cannot reproduce the headline 57 on 16. The
  manifest therefore declares Ethereum `callHandlers` on every Midas data
  source for the four setter functions, `setRoundData(int256)`
  (`0xa4381d1f`), `setRoundDataSafe(int256)` (`0x89d6e95f`) and the two
  three-argument variants (`0x2b6e02c7`, `0x92260352`). A call handler
  fires for a successful invocation of that function on that feed whether
  the call is the outer transaction or a nested call from a Safe,
  multicall or relayer, and it records the selector for (transaction,
  feed). The path rule of R6 becomes: the outer transaction's selector if
  the transaction targets the feed, else the selector recorded by the call
  handler for the same transaction and feed, else `UNKNOWN`. Ordering:
  graph-node runs a transaction's event triggers before its call triggers,
  so `handleAnswerUpdated` cannot read the call record; the call handler
  patches the Round(s) of its transaction after the fact. Implemented as
  R6a: Round keeps `@entity(immutable: true)` because graph-node accepts
  writes to an immutable entity inside the block that created it (schema
  documentation, "If changes happen in the same block in which the entity
  was created"); the call handler finds the Round through the `PostTx`
  record of (feed, transaction), and the Feed and Poster counters of R9
  are updated by whichever handler resolves the path. Expected effect on R17: `path:
  UNKNOWN` drops from at least 131 to the residue of transactions that
  neither target the feed nor pass through a setter call (expected 0),
  `path: UNCHECKED && !first && overBound` reaches 57 across 16 feeds. If
  Studio's mainnet indexers do not serve call handlers (unverified on
  2026-09-01; The Graph documents call handler support as network
  dependent), the fallback is stated plainly in the explorer, the demo and
  the submission: the Graph view carries the transaction-list base (29 on
  14) and the 57 is the engine's count from AnswerUpdated logs with the
  outer transaction unwrapped (02 R-series). Never present the two as one
  number without saying which base is on screen.
- C2. `Upgrade.withInitializer` cannot be known when the Upgrade is
  written. In an `upgradeAndCall` the proxy emits `Upgraded` before the
  initializer runs and emits `Initialized`, and handlers within a
  transaction run in log index order, so `handleUpgraded` runs first. R10
  is corrected as implemented: Upgrade keeps `@entity(immutable: true)`
  (same-block write, as in C1) and is written with `withInitializer: false`
  and id = feed address ++ transaction hash (one Upgrade per feed per
  transaction; the ProxyAdmin path never upgrades a feed twice in one
  transaction); `handleInitialized` loads the Upgrade with that id, if any,
  and sets `withInitializer: true`. The BoundChange of the same transaction
  is found by its `tx` field; no `boundChange` link is stored. The live test `g4_upgrades_with_initializer_match_the_value_changes`
  is unchanged in meaning: every `changed: true` BoundChange shares a
  transaction with an Upgrade whose flag is true after the sync completes.
- C3. Block variable in the query files (from blocker 3.3, owned by
  05 R1 and R2). The three query texts in R16 declare no block variable,
  so the agent cannot pin them without rewriting the text it hashes. Each
  query file declares `$block: Int!` and passes `block: {number: $block}`
  on every root field, including `_meta`, and a fourth file `Head` with
  `query Head { _meta { deployment hasIndexingErrors block { number hash
  timestamp } } }` gives the agent the head it pins to. See the
  corrections section of `05-consumer-agent.md` for the run sequence.
